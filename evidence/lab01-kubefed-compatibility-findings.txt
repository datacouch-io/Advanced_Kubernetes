KubeFed v0.10.0 helm chart against kind v1.37.0 (2026-09-01) -- reproducible failure

Attempt 1 (helm install, fresh namespace):
  server-side apply failed ... FederatedTypeConfig: webhook connection refused (webhook pod not yet ready -- expected transient race)

Attempt 2 (retry after webhook pod Ready):
  controller-manager CrashLoopBackOff
  F0901 10:31:47.437376 controller-manager.go:299] Error creating KubeFedConfig
    "kube-federation-system/kubefed": admission webhook "kubefedconfigs.core.kubefed.io"
    denied the request: spec.scope: Required value

Attempt 3 (full purge: helm uninstall + delete ns + delete all kubefed.io CRDs, then 2-pass helm upgrade --install):
  UPGRADE FAILED: failed calling webhook "federatedtypeconfigs.core.kubefed.io":
    failed to call webhook: Post https://kubefed-admission-webhook.kube-federation-system.svc:443/validate-federatedtypeconfigs?timeout=10s:
    tls: failed to verify certificate: x509: certificate signed by unknown authority
    (possibly because of "crypto/rsa: verification error" while trying to verify candidate authority certificate "kubefed-admission-webhook-ca")

Conclusion: KubeFed (archived by SIG Multicluster on 2023-04-25, kubernetes-retired/kubefed)
does not reliably install against a current-generation Kubernetes control plane (tested: kind v1.37.0).
Root cause pattern matches a known class of issue: self-signed webhook certs generated by
old (pre-2022, Go 1.16-era) code are rejected by the modern Go x509 verifier used in current
kube-apiserver/client-go builds. This is not an environment misconfiguration -- reproduced
identically across 3 full clean-slate attempts.

Follow-up test (2026-09-01): re-tested against kindest/node:v1.21.14 -- the Kubernetes
minor version KubeFed 0.9.x/0.10.0 actually targeted at the time of archival -- to isolate
whether the x509 failure was a "too new Kubernetes" problem. It was NOT: the identical
"x509: certificate signed by unknown authority ... kubefed-admission-webhook-ca" error
reproduced on v1.21.14 too. This rules out a Kubernetes-version incompatibility and points
instead to a bug in the kubefed-charts/kubefed:0.10.0 chart's own cert-generation hook --
most likely the pre-install/pre-upgrade Job that mints a new self-signed webhook CA does not
force the admission-webhook Deployment pod to restart and pick up the freshly rotated
Secret, leaving the ValidatingWebhookConfiguration's caBundle out of sync with the cert the
running pod actually serves. Deleting/restarting the webhook pod after the CA-rotation hook
runs did not resolve it either in this test, so the mismatch is not simply solved by a pod
restart on the client side.

Net result: this is a genuine, reproducible defect in the last published KubeFed chart, not
an artifact of this lab environment. Combined with the project's archived status (SIG
Multicloud retired it 2023-04-25, zero commits since), this is not something a training lab
should present as a "do this and it will work" exercise. See lab-01 document for how this
is handled: KubeFed is taught as a concept walkthrough (manifests + commands shown and
explained) rather than a live must-succeed exercise, and Cluster API (fully tested working,
see lab01-capi-workload-cluster.txt) carries the hands-on "provision real clusters" portion
of the lab.
